# 从校招焦虑到一个能跑的网络运维 Agent：我是怎么一步步把它做出来的

> 这篇不是宣传稿，是复盘。我会把每一次"为什么选 A 不选 B"、每一次踩坑、每一次推倒重来都写下来。如果你正在做类似的 AI Agent 项目，希望这些真实的犹豫能帮你少走弯路。

---

## 0. 起点：我为什么非要做这个项目

我是 2026 届毕业生，目标很明确：投华为、字节、腾讯的 AI 全栈/算法岗。

秋招前我翻了自己的简历，问题很明显：

- 课程项目都是"学生管理系统""图书借阅系统"这种，面试官三秒划走；
- 跟着教程做过一个 LangChain + OpenAI 的聊天机器人，README 里写着"企业级"，但我自己知道它换个问法就胡说；
- 我对"大模型应用到底能做什么、不能做什么"没有第一手体感。

我需要一个东西，满足三个条件：

1. **不是聊天玩具**——能让面试官相信我理解了 Agent 的边界；
2. **有真实系统**——不能全是 mock 数据，得接真的东西；
3. **我能讲清楚每一个技术决策**——面试官追问"你为什么不用 LangChain"时，我不能答"教程上就是这么写的"。

网络运维这个方向是我自己挑的。原因很实在：网络排障有天然的"取证→判断"结构，和 Agent 的 ReAct 范式完美对应；而且我学过计算机网络，OSPF/BGP 这些词不陌生，面试时能扛住追问。

## 1. 第一性原理：网络排障到底在做什么

先别急着写代码。我把一个真实的网络排障场景拆开看：

> **用户**："frr2 和 frr1 之间的 OSPF 邻居为什么断了？"
>
> **运维工程师**会做什么？
> 1. 先登 frr2，敲 `show ip ospf neighbor`，看邻居状态是不是 Full；
> 2. 登 frr1，看接口是不是 up；
> 3. ping 一下对端地址，看链路通不通；
> 4. 翻排障手册，"OSPF 邻居不建立"的常见原因有哪些；
> 5. 综合这些事实，下结论。

这个过程里有两个关键动作：

- **取证**：从设备拿到真实状态（邻居表、接口状态、路由表）；
- **查手册**：结合知识和历史经验判断原因。

如果我直接把用户这句话丢给 GPT，会发生什么？模型会一本正经地告诉我"OSPF 邻居不建立通常有以下原因：区域 ID 不匹配、Hello 间隔不一致、认证失败……"——它讲得头头是道，但它**根本不知道你现场这台设备现在是什么状态**。这就是纯 LLM 对话的硬伤：它在真空中推理。

所以我的第一个设计判断是：

> **Agent 必须能调用工具去读设备真实状态，拿到结果后再下结论。不能让它直接回答。**

这就是 ReAct（Reasoning + Acting）。我没有用 LangChain，因为我想自己把这个循环写一遍——这是后面所有技术决策的根。

## 2. 第一个版本：纯 ReAct 循环

我在 `backend/app/agent/agent.py` 里手写了一个循环，结构很简单：

```
while step < 6:
    1. 把用户问题 + 历史工具结果 拼成 prompt 给大模型
    2. 大模型返回 JSON：{action: "tool_name", args: {...}, thought: "..."}
    3. 我执行这个工具，把真实输出塞回上下文
    4. 如果模型说 "finish"，带最终答案退出
```

听起来简单，写起来全是坑。

### 坑 1：模型会编不存在的工具名

第一版我直接信任模型返回的 `action` 字段。结果模型有时候返回 `"check_ospf_status"`（我根本没这个工具），程序直接 KeyError 崩掉。

**修法**：在 `registry.py` 里做了一个工具注册表。执行前先查：这个工具名在不在表里？不在就把"可用工具清单"回灌给模型，让它重新选，最多重试 2 次。设备名也一样——模型有时候说"查 router_a"，但我的设备列表里只有 frr1/frr2/frr3，查不到就回灌。

这个"预校验 + 回灌"后来成了我跟面试官讲的一个亮点：**我不是相信模型输出，我是把它当成一个会犯错的下属，每次派活前都先核对工牌。**

### 坑 2：模型会编"工具结果"

更隐蔽的问题：模型有时候根本不调工具，直接在 `thought` 里写"根据我的观察，frr2 的 OSPF 邻居状态是 Full"——但它根本没看过真实数据。

**修法**：我在系统提示词里加了硬约束：

> "如果你没有调用过 show_ip_ospf 这个工具，禁止在回答中声称邻居状态。必须说'未获取到设备数据'。"

同时在代码层做了兜底：最终回答生成时，如果"取证步骤"是空的（一个工具都没调），就在回答前面自动加一行警告。

这个约束后来被面试官夸了一句"你知道 LLM 会幻觉"——其实我是被坑怕了。

## 3. 设备从哪来：为什么不是 EVE-NG，而是 FRR + Docker

这是整个项目里最纠结的一个决策。

### 选项 A：EVE-NG

EVE-NG 是真·网络仿真器，能跑华为 vRP、思科 IOS 镜像。面试官一听就懂。

但我查了一下：

- 要装 VMware + EVE-NG 本身（我电脑是 Windows，得装嵌套虚拟化）；
- vRP 镜像 1GB+，要到处找资源；
- 起一台虚拟路由器要分一份内存，三台就吃掉 6-8GB；
- 我这台开发机根本扛不住。

更现实的问题：**我的电脑上没装 EVE-NG**。一开始我想过在 EVE-NG 里建拓扑，但光是装环境就卡了两天，最后放弃。

### 选项 B：FRR + Docker

FRRouting（自由路由栈）是 Linux 上跑 OSPF/BGP/IS-IS 的开源实现。它不是华为，但它跑的是**真协议栈**——OSPF 邻居真的会从 Down 走到 Full，BGP 真的会交换路由前缀。

Docker 起三个容器：

```yaml
# docker-compose.frr.yml
frr1: image: frrouting/frr
frr2: image: frrouting/frr
frr3: image: frrouting/frr
```

每个容器里跑 zebra + ospfd + bgpd。容器之间用 docker network 连起来，IP 配好，协议起来后邻居表是真的。

**为什么这个折中我能接受？**

- 协议状态机是真的（OSPF Full/BGP Established 是真跑出来的，不是我手编的）；
- 一条命令 `docker exec frr1 vtysh -c "show ip ospf neighbor"` 就能拿邻居表；
- 三台容器加起来不到 300MB 内存，我笔记本跑得动；
- 面试时我可以诚实说："我用 FRR 是因为 EVE-NG 在我这台机器上装不起来；FRR 跑的协议栈是真的，但命令语法是开源社区的，不是华为 VRP。要接真华为设备，工具层换个 netmiko 驱动就行。"

**诚实地说"我没做什么、为什么没做"，比硬吹"企业级仿真"强一百倍。** 这是我做这个项目最大的体会。

## 4. 双通道设计：为什么业务 SSH 和带外 docker exec 要分开

接设备的方式我一开始只有一种：用 netmiko 走 SSH 登进去敲命令。

后来遇到一个问题：**如果我在 frr1 上注入了 `link_down` 故障，把它的 eth0 关了，业务通道的 SSH 是不是也连不上了？**

对。因为 SSH 就走在 eth0 上。你把接口 shutdown，自己也把自己的管理通道关了——这在真实网络里叫"把梯子踢了"。

真实运维怎么解决？两条通道：

- **业务通道**：走正常业务网（SSH）；
- **带外通道**：走独立管理网（Console 口、ILO、docker exec）。

我在代码里做成了双通道：

- `netmiko` 走 SSH，读接口/邻居/路由；
- `docker exec <container> vtysh` 走带外，即使业务接口 down 了也能进容器敲命令。

这两个通道在 `tools.py` 里互相 fallback：SSH 失败了自动切 docker exec。

这个设计不是我一开始想出来的，是注入故障时把自己 SSH 关了、慌了半天后想明白的。**好的架构很多时候不是设计出来的，是被坑出来的。**

## 5. RAG：排障手册怎么接进来

光有工具不够。模型看到"frr2 OSPF 邻居 Down"的原始输出，不一定知道该怎么解释。它需要排障手册的知识。

### 5.1 为什么用 RAG 不用微调

这个判断很简单：

- 我的知识库是几份 PDF 手册（华为/思科的 OSPF/BGP 排障指南），加起来 20 多份；
- 微调要标注数据、要 GPU、要训练——我没有；
- RAG 是检索，改知识库直接换文件，不用重训。

### 5.2 Embedding 选型：这是最折腾的一段

一开始我用智谱的 `embedding-3` API。跑了两天发现一个问题：**免费额度每天 200 万 token，池子空了就 429**。我做测试时一次检索要编码几百段，很快就撞墙。

而且我查了一下，智谱的免费 token 池是全局的，不是按模型分——你用 glm-4-flash 聊天和 embedding 共用一个池。这哪是免费？

**最后我切到了本地模型 bge-small-zh-v1.5**：

- 512 维向量，中文效果不错；
- 下载下来 100MB，CPU 跑编码也就几十毫秒；
- 完全离线、免费、不撞额度。

切换成本比我想的低：在 `embedding.py` 里加了一个分支，`ZHIPU_EMBEDDING_MODEL=bge` 就走本地 SentenceTransformer，否则走智谱 API。

**教训**：云 API 免费额度听着香，但做开发/测试时频繁调用，很快就发现"免费"是有条件的。本地小模型是学生党最稳的选择。

### 5.3 混合检索：为什么不用纯向量

我做了评测才发现纯向量检索有问题。

纯向量语义相似度在"问法变了"的时候会拉胯。比如：

- 标准问法："OSPF 邻居不建立怎么排查"
- 口语问法："为啥这俩路由邻居一直起不来"
- 极简问法："OSPF Down"
- 带噪音："求问一下 ospr 邻居为啥断了"（还拼错了）

纯向量对口语和拼写错误的召回明显下降。

所以我做了**混合检索**：

- 一路 BM25（关键词匹配，对"ospf_cost"这种专有名词稳）；
- 一路向量检索（语义匹配，对口语问法好）；
- 两路结果用 RRF（Reciprocal Rank Fusion）融合。

我自己标了 96 条问答对，覆盖 5 种问法。结果是：

| 检索方式 | R@5 | MRR |
|---------|-----|-----|
| 纯向量 | 0.865 | 0.680 |
| 混合检索 | **0.990** | **0.748** |

R@5 从 0.865 提到 0.990，在最烂的口语问法上提升最大。**如果不做评测，我根本不知道混合检索到底有没有用——我会凭感觉说"应该更好吧"。** 这是我做这个项目学会的第二件事：不量化的优化都是自嗨。

## 6. 安全门：为什么注入故障前必须先 dry-run

这是我做过最有"运维感"的一个设计。

一开始我让 Agent 直接注入故障：说"在 frr1 上 shutdown eth0"，程序就执行。后来我意识到一个问题：

**LLM 是会犯错的。** 如果它理解错了，在 frr3 的生产接口上执行了 shutdown，后果是什么？

我加了一个 `dry_run` 动作：

1. Agent 说要注入故障时，系统先返回一段"将要执行什么命令、影响哪个接口、预计什么后果"；
2. 60 秒内，必须有一次 `dry_run` 请求过这个 (设备, 故障, 接口) 组合；
3. 没预览过就直接 inject，**直接拒绝执行**。

这个逻辑写在 `fault_state.py` 里，用 `has_fresh_dry_run()` 判断。

面试时我讲这个设计，面试官说"这像真实 NOC 的变更窗口"——我开心了很久。其实它的核心思想很朴素：**让模型在动手前先说一遍要做什么，人确认过了再干。**

## 7. 并发与持久化：被两个 bug 教做人

### 7.1 并发丢更新

第一版 `fault_state.json` 是直接读→改→写。两个请求同时进来：

- 请求 A 读到 `{frr1: {}}`
- 请求 B 读到 `{frr1: {}}`
- A 写入 `{frr1: {ospf_cost: eth0}}`
- B 写入 `{frr2: {link_down: eth0}}`——把 A 的覆盖了

A 的故障记录丢了。

**修法**：所有读改写操作包一个 `threading.Lock()`。session_store 也一样。我在 `/api/health` 里把 `process.pid` 暴露出来，承认这是**单进程内的锁**——多进程/多用户场景下设备级互斥要靠上层调度，这个边界我清楚。

### 7.2 kill -9 留半写 JSON

更阴的 bug：直接 `json.dump` 写文件，写到一半进程被 kill（比如我关终端），文件就成了半截 JSON。下次启动 `json.load` 直接抛 JSONDecodeError。

**修法**：atomic write——先写 `fault_state.tmp`，写完再 `os.replace(tmp, fault_state.json)`。`os.replace` 在 Windows/Linux 上都是原子操作：要么旧文件在，要么新文件在，不会有中间状态。

同时 `_load` 加了兜底：JSON 解析失败就返回空字典，不让程序起不来。

这两个 bug 让我理解了一件事：**单机程序的"看起来能跑"和"不会在用户关机时崩"是两回事。**

## 8. 前端与桌面壳：从 921 行单文件到 pywebview

### 8.1 为什么不引 React/Vue

第一版前端是一个 921 行的 `index.html`，HTML/CSS/JS 全堆在里面。写到后面我自己都不想维护。

我认真考虑过引 React + Vite，但算了一下：

- 我的前端就是一个聊天框 + 一个拓扑图 + 几个按钮，没有复杂状态；
- 引 React 意味着要装 node、要构建、要打包，对一个单机桌面应用是杀鸡用牛刀；
- 原生 ES Module 现代浏览器全支持，零构建。

**修法**：拆成三个文件：

- `index.html`（91 行结构）
- `styles.css`（172 行样式）
- `js/app.js`（655 行逻辑，原生 ES Module）

不引框架，不是我不会，是这个场景下框架本身是负担。

### 8.2 为什么用 pywebview 打包成 exe

用户不想在浏览器里开 http://127.0.0.1:8000——他想要一个"双击就用"的桌面应用。

方案：

- 用 PyInstaller 把 Python 后端打成 exe；
- 前端用 pywebview 开一个原生窗口（基于系统 WebView2），不显示浏览器地址栏；
- 双击 `NetOpsAssistant.exe` 就能用。

**踩坑**：PyInstaller 打包时会把 torch（sentence-transformers 依赖）也打进去，exe 从 50MB 变成 1.2GB。解决方法是在 spec 里 `excludes=['torch']`——但我又用 bge 做 embedding……最后做成了"打包版走降级 embedding，开发版走本地 bge"。这是个不完美但可工作的妥协。

## 9. 测试与 CI：被 GitHub Actions 教做人

### 9.1 58 个测试

我写了 11 个测试文件，58 个用例：

- `test_agent_loop.py`：mock LLM 决策序列，断言工具真被调、幻觉工具被拒绝；
- `test_fault_gate.py`：dry-run 安全门；
- `test_frr_integration.py`：真 FRR 容器集成测试（标了 `@pytest.mark.dock`，CI 里跳过）；
- `test_robustness.py`：各种离谱输入（空消息、超长消息、奇怪字符）；
- `test_eval_smoke.py`：RAG 评测静态校验。

### 9.2 CI 踩的四个坑

第一次配 GitHub Actions，红了快十次。每一次都是不同的问题：

1. **PowerShell 正则把测试函数名吃了**：我写 PowerShell 脚本批量改测试，替换时 `$1` 变量展开成空，把 `def test_xxx` 这行整个删了，pytest collect 阶段直接语法错误。
2. **Python 3.11 不兼容 sentence-transformers 6.x**：本地是 3.14 没事，CI 用 3.11 直接 import 失败。换成 3.12 才好。
3. **CI 没设环境变量走了智谱 API**：我设了 dummy key，但默认 embedding model 是 `embedding-3`，它拿着 dummy key 去调智谱，401。加 `ZHIPU_EMBEDDING_MODEL=bge` 走本地模型才过。
4. **requirements.txt 漏了 pymupdf**：`app/rag/ingest.py` 要解析 PDF，但我忘了把 pymupdf 写进 requirements，CI 上 `ModuleNotFoundError`。

**教训**：CI 红不是坏事，它就是在告诉你"你以为能跑的环境，别人那跑不起来"。每一个红都是一次真实的 bug。

最后 CI 绿了，覆盖率 51%——我没吹成 95%，sim_ssh.py（仿真 SSH 服务端）0%、evaluate.py（评测脚本本身）16% 我都老实写在 README 里。

## 10. 最终交付了什么

一个 FastAPI 后端 + 原生前端 + pywebview 桌面壳的单机应用：

- **手写 ReAct 循环**：不引 LangChain，工具名/设备名预校验，trace 落盘；
- **真实 FRR 协议栈**：3 个 Docker 容器跑 OSPF/eBGP，邻居表是真的；
- **混合检索 RAG**：本地 bge + BM25 + RRF，R@5=0.990；
- **双通道设备访问**：netmiko SSH + docker exec vtysh 互为 fallback；
- **dry-run 安全门**：60 秒预览过才允许注入故障；
- **并发保护**：threading.Lock + atomic write；
- **指标埋点**：P50/P95 延迟、token 用量、错误率落盘；
- **CI 绿**：GitHub Actions 自动跑 58 个测试，覆盖率 51%。

### 我诚实承认的边界

- **单机单进程**：锁是进程内的，多用户/多实例要靠 Redis/PG，我没做；
- **FRR 不是华为**：协议栈是真的，但命令语法是开源社区的，不是 VRP；
- **覆盖率 51%**：边缘模块（仿真 SSH、webhook）没有自动化测试；
- **没有 e2e 视频**：面试官如果问"能跑给我看吗"，我得现场起 Docker。

## 11. 这个项目教给我的事

**第一件**：不要相信教程上的"企业级"。自己写一遍 ReAct，你才知道模型会在哪些地方犯错、为什么需要工具校验、为什么需要 trace。

**第二件**：诚实比包装值钱。我说"我没接 EVE-NG 因为装不起来"比吹"我做了华为仿真"强——因为面试官两句话就能戳穿后者，但前者他会觉得你清楚自己在做什么。

**第三件**：不量化的优化都是自嗨。如果没标那 96 条问答对，我会凭感觉说"混合检索应该更好"，而不是拿 R@5=0.990 这个数字说话。

**第四件**：CI 是朋友不是敌人。它红的每一次，都是你在自己电脑上发现不了的 bug。

这个项目现在在我 GitHub 上（LJY20030728/netops-ai-assistant），58 个测试、CI 绿、README 里有 Mermaid 架构图。它不是完美的，但它是我自己一行一行写出来的——每一个技术决策我都能讲清楚为什么这么选、为什么不选另一个、边界在哪。

这就够了。校招面试，要的不是一个完美的系统，是一个能让你讲 30 分钟不被问倒的系统。
