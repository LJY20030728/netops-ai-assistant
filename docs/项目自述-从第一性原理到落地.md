# 我为什么写这个东西：一个实习生对主管审批工作的观察

> 这篇不是宣传稿，是复盘。我会写清楚这个东西是怎么来的、每一步为什么这么选、踩了什么坑、以及它
>
> **不是什么**
>
> 。



***

## 0. 它是怎么来的

2026 年 7 月，我开始在中金财富技术部做网络工程师实习生，一直做到现在。

带我的主管每天的工作里有一块很耗时间：**在公司自研的网络管理系统上审批一大堆请求**。扩容、割接、故障处理、配置变更 —— 每条都要他登系统、看设备状态、对照手册、判断能不能批、批了之后还要跟进结果。一天下来几十条，很多是重复劳动：同一个 OSPF 邻居问题翻来覆去出现，同样的排障步骤他一天要敲好几遍。

我坐在他旁边看了一周，发现一个事：他做的事情有固定套路 ——**先查设备状态，再对照手册，然后下结论**。这个套路人做很累，但机器做其实不难。

我就想：能不能写个东西，让他用自然语言问一句，系统自己去把设备状态读回来、把相关手册段落找出来、给他一个带证据的回答？

这就是这个项目的起点。**它不是我为了校招硬凑的练手项目，是我在实习期间观察到一个真实的人的真实痛点后，试着用技术去解决。**



***

## 1. 先说清楚它现在是什么、不是什么

这点我必须诚实，免得你看完期待错了：



* **它现在是一个本地原型**，跑在我自己的笔记本上，用开源技术搭的；

* **它没有接进中金的生产网络管理系统**—— 那涉及权限、数据隔离、安全审计，一个实习生不可能在生产环境随便部署东西；

* 我用 Docker 起了三台跑真实路由协议栈的容器来模拟设备，用本地小模型做知识库检索，验证 "Agent 读设备状态 + 查手册 + 给带证据的回答" 这条路走不走得通；

* **它的价值是验证思路，不是已经上线的工具。** 但思路是真的 —— 我主管的痛点是真的，排障流程是真的，只是落地环境换成了我自己能控制的沙箱。



***

## 2. 第一性原理：主管审批时到底在做什么

我把他的工作拆了一下。一个典型的审批请求进来，他做的事是：

> **请求**
>
> ："frr2 和 frr1 之间的 OSPF 邻居为什么断了？要批割接吗？"
> **他做的**
>
> ：
> 登 frr2，敲 
>
> `show ip ospf neighbor`
>
> ，看邻居状态是不是 Full；
> 登 frr1，看接口是不是 up；
> ping 一下对端地址；
> 翻排障手册，"OSPF 邻居不建立" 的常见原因；
> 综合这些事实，判断能不能批。

这里有两个关键动作：



* **取证**：从设备拿真实状态；

* **查手册**：结合知识判断原因。

如果我直接把这句话丢给 GPT，会发生什么？模型会头头是道地告诉我 "OSPF 邻居不建立通常有以下原因：区域 ID 不匹配、Hello 间隔不一致……"—— 但它**根本不知道现场这台设备现在是什么状态**。这在审批场景里是致命的：你不能对着一个不知道现场情况的回答做变更决策。

所以我的第一个判断是：

> **Agent 必须自己去读设备真实状态，拿到证据之后再下结论。不能让它凭空回答。**

这就是 ReAct（Reasoning + Acting）。我没有用 LangChain，因为我想自己把这个循环写一遍 —— 我得搞清楚它在什么地方会犯错，才知道怎么在审批场景里用得放心。



***

## 3. 第一个版本：手写 ReAct 循环

在 `backend/app/agent/agent.py` 里写了一个循环：



```
while step < 6:

&#x20;   1\. 把用户问题 + 历史工具结果 拼成 prompt 给大模型

&#x20;   2\. 大模型返回 JSON：{action, args, thought}

&#x20;   3\. 执行这个工具，把真实输出塞回上下文

&#x20;   4\. 模型说 finish，带最终答案退出
```

写起来全是坑。

### 坑 1：模型会编不存在的工具名

第一版直接信任模型返回的 `action`。结果它有时候返回 `"check_ospf_status"`—— 我根本没这个工具，程序直接 KeyError 崩掉。

**修法**：在 `registry.py` 做了个工具注册表。执行前先查：这个工具名在不在表里？不在就把 "可用工具清单" 回灌给模型，让它重新选，最多重试两次。设备名也一样 —— 模型有时候说 "查 router\_a"，但我的设备列表里只有 frr1/frr2/frr3，查不到就回灌。

这个设计后来我自己觉得挺实在：**我不是相信模型输出，我是把它当成一个会犯错的下属，每次派活前先核对工牌。** 审批场景里这一点特别重要 —— 你不能让一个会幻觉的东西直接对生产设备发命令。

### 坑 2：模型会假装自己看过了

更隐蔽的问题：它有时候根本不调工具，直接在回答里写 "根据我的观察，frr2 的 OSPF 邻居状态是 Full"—— 但它根本没看过真实数据。

**修法**：系统提示词里加了硬约束：没调过 `show_ip_ospf` 就禁止声称邻居状态，必须说 "未获取到设备数据"。代码层也兜底：如果一个工具都没调，回答前面自动加警告。

## 4. 设备从哪来：为什么是 FRR + Docker

我一开始想过用 EVE-NG（真・网络仿真器，能跑华为 / 思科镜像）。但：



* 要装 VMware + EVE-NG，我的笔记本扛不住；

* 华为镜像要到处找资源；

* 起一台虚拟路由器吃一份内存，三台就 6-8GB。

更现实的问题：**我不可能在实习期间往主管的生产环境里装仿真器。** 我只能在自己电脑上搭沙箱。

最后选了 FRRouting——Linux 上跑 OSPF/BGP 的开源路由栈。Docker 起三个容器，容器之间用 docker network 连起来，协议起来后邻居表是真的：



```
\# docker-compose.frr.yml

frr1, frr2, frr3: image: frrouting/frr
```

**为什么这个折中我能接受？**



* 协议状态机是真的 ——OSPF 邻居真的会从 Down 走到 Full，BGP 真的会交换路由前缀；

* 一条 `docker exec frr1 vtysh -c "show ip ospf neighbor"` 就能拿邻居表；

* 三台容器加起来不到 300MB，我笔记本跑得动；

* 演示时我可以诚实说："FRR 跑的协议栈是真的，但命令语法是开源社区的，不是华为 VRP。要接真设备，工具层换个 netmiko 驱动就行。"

**诚实地说 "我没做什么、为什么没做"，比硬吹 "企业级仿真" 强。** 这是我实习期间最大的体会 —— 主管不会因为你说 "企业级" 就高看你，他会因为你说清楚边界而信任你。



***

## 5. 双通道：为什么 SSH 和 docker exec 要分开

接设备的方式一开始只有一种：netmiko 走 SSH。

后来遇到一个问题：**如果我在 frr1 上注入&#x20;**`link_down`**&#x20;故障把 eth0 关了，SSH 是不是也连不上了？**

对。SSH 就走在 eth0 上。你把接口 shutdown，自己也把自己的管理通道关了 —— 这在真实网络里叫 "把梯子踢了"。主管审批割接时最怕的就是这个：你改了配置，然后自己也登不上去了。

真实运维怎么解决？两条通道：



* **业务通道**：走正常业务网（SSH）；

* **带外通道**：走独立管理网（Console 口、ILO、docker exec）。

我在代码里做成双通道：netmiko 走 SSH，docker exec 走带外，互相 fallback。

这个设计不是我一开始想出来的，是注入故障时把自己 SSH 关了、慌了半天后想明白的。**好的架构很多时候不是设计出来的，是被坑出来的。**

## 6. 知识库：主管翻的那些手册怎么接进来

光有工具不够。模型看到 "frr2 OSPF 邻居 Down" 的原始输出，不一定知道怎么解释。它需要排障手册的知识 —— 就是主管平时翻的那些。

### 为什么用 RAG 不用微调



* 我的知识库是几十份排障手册（华为 / 思科的 OSPF/BGP 指南）；

* 微调要标注数据、要 GPU、要训练 —— 我一个实习生没有；

* RAG 是检索，改知识库直接换文件，不用重训。

### Embedding 选型：免费额度的坑

一开始用智谱的 `embedding-3` API。跑了两天发现：**免费额度每天 200 万 token，池子空了就 429**。我做测试时一次检索要编码几百段，很快撞墙。而且免费 token 池是全局的，聊天和 embedding 共用 —— 这哪是免费？

最后切到本地模型 `bge-small-zh-v1.5`：512 维、100MB、CPU 跑几十毫秒、完全离线免费。切换成本比想的低，在 `embedding.py` 加个分支就行。

**教训**：云 API 免费额度听着香，但开发测试时频繁调用，很快发现 "免费" 是有条件的。本地小模型是学生党最稳的选择。

### 混合检索：不做评测不知道有没有用

我做了评测才发现纯向量检索有问题。纯向量对口语化问法和拼写错误的召回明显下降 —— 比如 "为啥这俩路由邻居一直起不来" 和 "OSPF Down"，纯向量给的结果不一样。

所以做了**混合检索**：BM25（关键词，对 "ospf\_cost" 这种专有名词稳）+ 向量（语义，对口语好），两路用 RRF 融合。

我自己标了 96 条问答对，覆盖 5 种问法。结果：



| 检索方式 | R@5       | MRR       |
| ---- | --------- | --------- |
| 纯向量  | 0.865     | 0.680     |
| 混合检索 | **0.990** | **0.748** |

**如果不做评测，我会凭感觉说 "应该更好吧"。** 这是我做这个项目学会的第二件事：不量化的优化都是自嗨。主管问 "你这个检索到底准不准"，我不能说 "感觉还行"，我得给他数字。

## 7. 安全门：审批场景里最重要的设计

这是我做过最有 "审批感" 的设计。

一开始我让 Agent 直接注入故障。后来意识到：**LLM 是会犯错的。** 如果它理解错了，在错误的设备上执行了 shutdown，后果是什么？主管审批时最怕的就是 "没确认就动手"。

我加了一个 `dry_run` 动作：



1. Agent 说要注入故障时，系统先返回 "将要执行什么命令、影响哪个接口、预计什么后果"；

2. 60 秒内必须有一次 `dry_run` 请求过这个组合；

3. 没预览过就直接 inject，**直接拒绝执行**。

这个逻辑写在 `fault_state.py` 里。它的核心思想很朴素：**让模型在动手前先说一遍要做什么，人确认过了再干。** 这就是主管审批流程的缩影。

## 8. 并发与持久化：被两个 bug 教做人

### 并发丢更新

第一版 `fault_state.json` 直接读→改→写。两个请求同时进来，后写的把先写的覆盖了。

**修法**：所有读改写操作包一个 `threading.Lock()`。我在 `/api/health` 里把 `process.pid` 暴露出来，承认这是**单进程内的锁**—— 多进程 / 多用户场景下设备级互斥要靠上层调度，这个边界我清楚。

### kill -9 留半写 JSON

更阴的 bug：直接 `json.dump` 写文件，写到一半进程被 kill，文件就成了半截 JSON，下次启动直接崩。

**修法**：atomic write—— 先写 `.tmp`，写完再 `os.replace`。`os.replace` 是原子操作：要么旧文件在，要么新文件在，不会有中间状态。

这两个 bug 让我理解了一件事：**单机程序的 "看起来能跑" 和 "不会在用户关机时崩" 是两回事。** 主管不会关心你代码写得多优雅，他只会关心你关了窗口再打开，数据还在不在。

## 9. 前端与桌面壳

### 为什么不引 React/Vue

第一版前端是一个 921 行的 `index.html`，写到后面自己都不想维护。

我认真考虑过引 React + Vite，但算了一下：我的前端就是一个聊天框 + 一个拓扑图 + 几个按钮，没有复杂状态。引 React 意味着装 node、要构建、要打包，对一个单机桌面应用是杀鸡用牛刀。原生 ES Module 现代浏览器全支持，零构建。

**修法**：拆成 `index.html`（92 行）+ `styles.css`（178 行）+ `js/app.js`（678 行）。不引框架不是不会，是这个场景下框架本身是负担。

### 为什么用 pywebview 打包成 exe

主管不想在浏览器里开 `http://127.0.0.1:8000`—— 他想要一个 "双击就用" 的东西。用 PyInstaller 打 exe，pywebview 开原生窗口，不显示浏览器地址栏。

**踩坑**：PyInstaller 会把 torch 也打进去，exe 从 50MB 变成 1.2GB。解决方法是 spec 里 `excludes=['torch']`—— 但我又用 bge 做 embedding…… 最后做成了 "打包版走降级 embedding，开发版走本地 bge"。这是个不完美但可工作的妥协。

## 10. 测试与 CI

我写了 9 个单元测试文件 + 21 个 e2e 测试文件，共 58 个用例（本地跑 55 passed + 3 skipped，3 个是需要 Docker 的集成测试）：ReAct 循环真测试、dry-run 门、FRR 集成测试（标了 mark，CI 里跳过）、各种离谱输入的鲁棒性测试。

第一次配 GitHub Actions，红了快十次。每一次都是不同的问题：



1. PowerShell 正则把测试函数名吃了，pytest collect 直接语法错误；

2. Python 3.11 不兼容 sentence-transformers 6.x，换 3.12 才好；

3. CI 没设环境变量走了智谱 API，dummy key 直接 401；

4. requirements.txt 漏了 pymupdf，CI 上 `ModuleNotFoundError`。

**教训**：CI 红不是坏事，它就是在告诉你 "你以为能跑的环境，别人那跑不起来"。每一个红都是一次真实的 bug。

最后 CI 绿了，覆盖率 51%—— 我没吹成 95%，sim\_ssh 0%、evaluate 16% 都老实写在 README 里。

## 11. 它现在到底能做什么

一个 FastAPI 后端 + 原生前端 + pywebview 桌面壳的本地应用：



* **手写 ReAct 循环**：不引 LangChain，工具名 / 设备名预校验，trace 落盘；

* **真实 FRR 协议栈**：3 个 Docker 容器跑 OSPF/eBGP，邻居表是真的；

* **混合检索 RAG**：本地 bge + BM25 + RRF，R@5=0.990；

* **双通道设备访问**：netmiko SSH + docker exec vtysh 互为 fallback；

* **dry-run 安全门**：60 秒预览过才允许注入故障；

* **并发保护**：threading.Lock + atomic write；

* **指标埋点**：P50/P95 延迟、token 用量、错误率落盘；

* **CI 绿**：GitHub Actions 自动跑 55 个测试，覆盖率 51%。

### 我诚实承认的边界



* **单机单进程**：锁是进程内的，多用户 / 多实例要靠 Redis/PG，我没做；

* **FRR 不是华为**：协议栈是真的，但命令语法是开源社区的，不是 VRP；

* **没接进中金生产系统**：这是我在自己电脑上搭的沙箱，验证思路用；

* **覆盖率 51%**：边缘模块没有自动化测试。

## 12. 这个项目教给我的事

**第一件**：技术是为人服务的。我做这个东西不是为了写一个 "牛的项目"，是因为我坐在主管旁边看了一周，觉得他每天重复敲那些命令太累了。这个出发点比任何技术栈都重要。

**第二件**：诚实比包装值钱。我说 "我没接进生产环境因为权限不够" 比吹 "我做了企业级运维平台" 强 —— 因为主管两句话就能戳穿后者，但前者他会觉得你清楚自己在做什么。

**第三件**：不量化的优化都是自嗨。如果没标那 96 条问答对，我会凭感觉说 "混合检索应该更好"，而不是拿 R@5=0.990 这个数字说话。

**第四件**：CI 是朋友不是敌人。它红的每一次，都是你在自己电脑上发现不了的 bug。

这个项目现在在我 GitHub 上。它不是完美的，但它是我在实习期间，观察到一个真实的人的真实痛点后，一行一行写出来的 —— 每一个技术决策我都能讲清楚为什么这么选、为什么不选另一个、边界在哪。

这就够了。
