# 10 分钟面试演示脚本

> 用法：面试当天照这个走，每步标了时间、操作、预期、话术。
> 详细背景见 `演示手册.md`，翻车预案在最后。

---

## 0:00–0:30 开场：启动器（30 秒）

**操作**：双击 `NetOpsLauncher.exe`。

**你看到**：控制台逐行打印 Docker 检查 → 容器已运行 → 后端启动 → 浏览器自动打开 `127.0.0.1:8000`。

**话术**：
> "这是一个 Windows 桌面应用，双击就跑。它先检查 Docker 引擎状态，再拉起 3 台 FRR 路由器容器，最后启动 FastAPI 后端并打开界面。每一行日志都是真实检查，不是假进度条。"

---

## 0:30–2:00 真实拓扑（1.5 分钟）

**操作**：切到「仅拓扑」tab，点「立即刷新」。

**你看到**：
- frr1/frr2/frr3 三个节点全绿
- frr1 标 `OSPF: 2.2.2.2 Full/DR`
- frr2 标 `OSPF Full` + `eBGP: 10.0.23.3 Established`
- 卡片里有真实邻居表和路由表（`O>* 2.2.2.2/32 [110/10] via 10.0.12.3`）

**话术**：
> "这不是画出来的拓扑图。每个数字都是后端实时 SSH 进 FRR 容器跑 `show ip ospf neighbor` / `show bgp summary` 解析出来的。FRR 是生产级开源路由栈，很多厂商用它做数据面，比模拟软件更接近真实。"

**加分**：右上角那个小标签——"P50/P95 延迟、今日 token、错误率"，指一下：
> "这是我加的请求级 metrics，每次 chat 的延迟分解和 token 用量都落盘，P95 一眼看到。"

---

## 2:00–5:00 Agent 故障演练（3 分钟，核心）

**操作**：切到「分栏」或「仅对话」，输入：

> 在 frr1 上做一次真实故障演练：先 status 看基线，再 inject link_down eth0，取证确认 OSPF 邻居消失，最后 recover 恢复并复验

**你看到**（流式输出）：
1. Agent 调 `frr_fault_inject action=status` → 返回邻居 Full
2. Agent 调 `action=inject link_down eth0` → 真实执行 `docker exec frr1 ip link set eth0 down`
3. Agent 调 `action=show`（走 docker exec 带外通道）→ 邻居消失
4. **切到拓扑页**：frr1 变红灰，OSPF 路由消失
5. Agent 调 `recover` → 恢复
6. 拓扑刷新 → 节点回绿

**话术（讲透三点）**：

> ① **双通道设计**：`ip link set down` 会切断 SSH（业务=管理面），所以读走 SSH、写走 docker exec 带外——类比机房 console 口 / ILO。这是真实运维设计，不是玩具。
>
> ② **ReAct 闭环**：模型每步决策都基于上一步工具的真实返回，先取证再下结论。左侧能看到它的思考过程（thinking 事件流）。
>
> ③ **安全门**：inject 前必须先 dry-run 预览，60 秒内没预览过直接拒绝。这是从"误操作是 NOC 最大事故"这个真实约束倒推的。

**如果翻车**：点拓扑页「一键恢复」按钮，这是 admin 幂等兜底。

---

## 5:00–6:30 RAG 知识库（1.5 分钟）

**操作**：问一个知识类问题：

> 出口带宽打满应该查哪些指标？

**你看到**：
- 回复上方有 `sources` 卡片，列出 2-3 个来源文档名和相关度分数
- 回答内容引用了手册原文

**话术**：
> "RAG 不是黑盒。我有 96 条标注评测集，混合检索（向量+BM25）的 Recall@5 是 0.990，纯向量只有 0.865——这是为什么选混合检索而不是只塞 embedding。回答带 sources 引用，不编造。"

---

## 6:30–8:30 工程亮点（2 分钟，面试官最在意）

**操作**：不需要操作，纯讲。对着代码仓库讲：

> 我挑几个工程决策讲：
>
> ① **手写 ReAct 而不是 LangChain**——核心循环 300 行，每一步 thought/tool/finish 都落盘成 trace.jsonl，"模型为什么这步调这个工具"可复盘。LangChain 的调度是黑盒，面试讲不清。
>
> ② **幻觉双层防护**——提示词软约束 + 工具层硬校验。模型编了不存在的工具名或设备名，registry 直接拒绝执行，把可用清单回灌给它重试，最多 2 次。这三个行为都有单元测试。
>
> ③ **并发与边界诚实**——关键写路径加了 threading.Lock；`/api/health` 暴露 PID 和 worker 数，明示单进程单机。不写"企业级高可用"，因为这个规模引入 Redis 是过度工程。
>
> ④ **测试**——58 个测试，其中 agent loop 3 个真集成测试（mock LLM 决策序列，断言工具真被调、结果真回灌），RAG 96 条评测，dry-run gate 3 个用例。

---

## 8:30–10:00 边界与下一步（1.5 分钟）

**话术**：
> "这个系统的边界我很清楚：单进程单机、Docker 在本地、没有多副本一致性。它定位是'网络运维 Agent 的闭环验证平台'——证明 LLM 经工具调用能操作真实协议栈并对结果负责。下一步如果要扩展：状态层已经在 session_store/store/fault_state 三个门面后面，换 SQLite 不动业务代码；agent loop 要并行工具调用也可以在现有手写循环上加。"

## 翻车预案（记不住就看这里）

| 现象 | 处理 |
|------|------|
| 对话不回复 / API 报错 | 网络/key 问题，直接说"对话非核心，看拓扑"，跳场景二 |
| 拓扑节点灰色 | 等 30 秒自动刷新；点刷新；再不行双击启动器 |
| Agent 说"设备不可用" | 这是设计好的拦截，顺势讲"模型想乱连仿真设备，工具层拦住了"——加分 |
| 演练后设备还是红的 | 点「一键恢复」 |
| 全部失败 | 双击启动器 → 打开拓扑页 → 讲"真实 FRR + RAG + ReAct 完整系统"，依然成立 |
