**备注（必须诚实说明的两点）**：
1. **test_scenarios_api 必须在 simulate 模式跑**（`DEVICE_MODE=simulate` 启动后端）。在 real 模式下跑会出现 12 项失败——那是"模式不匹配"，不是产品缺陷。切换模式重跑即 16/0。
2. **test_rbac_api 需要独立的 auth 实例**（`python tests/_auth_server.py`，监听 8001），且**必须以 `DEVICE_MODE=simulate` 启动**——RBAC 断言依赖仿真设备工具调用成功/被拒的区分，real 模式下仿真设备会被 guard 硬拒导致 operator 断言误挂。已按此方式补跑：**10/0 通过**。

## 二、测试环境与命令（可复现）

### 前置（一次性）
```powershell
# 项目根目录
docker compose -f docker-compose.frr.yml up -d     # 3 台 FRR 容器
cd backend; Copy-Item .env.example .env            # 填 ZHIPU_API_KEY
```

### 快速回归组（无 LLM 调用，约 3-5 分钟）
```powershell
cd backend
$env:DEVICE_MODE="real"
# 先起后端（同一命令窗口内起+测，跨窗口进程会被回收）：
Start-Process ..\.venv\Scripts\python.exe -ArgumentList "-X","utf8","-m","uvicorn","app.main:app","--host","127.0.0.1","--port","8000" -WindowStyle Hidden
Start-Sleep 8
..\.venv\Scripts\python.exe -X utf8 tests\test_frr_lab.py       # 9/0
..\.venv\Scripts\python.exe -X utf8 tests\test_frr_e2e.py       # 8/0
..\.venv\Scripts\python.exe -X utf8 tests\test_engineering_api.py  # 17/0
```

### 模式切换测试（场景 API）
```powershell
# 杀 real 后端 → 以 simulate 起 → 跑 → 杀 → 恢复 real
$env:DEVICE_MODE="simulate"
# （同上 Start-Process 起后端）
..\.venv\Scripts\python.exe -X utf8 tests\test_scenarios_api.py  # 16/0
```

### 慢速 LLM 组（真实模型调用，10-30 分钟，联网）
```powershell
..\.venv\Scripts\python.exe -X utf8 tests\test_security_api.py    # 14/0（含 3 次对话）
..\.venv\Scripts\python.exe -X utf8 tests\test_rag_expanded.py    # 8 场景命中
# RBAC 需 auth 实例（关键：DEVICE_MODE=simulate，否则仿真设备被 guard 拒导致断言误挂）：
$env:DEVICE_MODE="simulate"
Start-Process ..\.venv\Scripts\python.exe -ArgumentList "-X","utf8","tests\_auth_server.py" -WorkingDirectory $PWD -WindowStyle Hidden
Start-Sleep 8
..\.venv\Scripts\python.exe -X utf8 tests\test_rbac_api.py        # 8001，四角色，10/0
```

### 一键编排脚本（已有，含已知限制）
`backend/tests/run_tests.ps1` 自动完成"起后端→跑测试→停→切模式→汇总"。
- 用法：`powershell -ExecutionPolicy Bypass -File backend\tests\run_tests.ps1 -Quick`（快速组）
- **已知限制**：脚本内 `Run-Test` 的 `*>` 输出重定向在部分环境会挂起（实测卡住一次）；若脚本长时间无输出，改用上面的分步命令。此限制已记录，不作为产品缺陷。
- 脚本含编码坑教训：PowerShell 5.1 读 UTF-8 无 BOM 脚本会乱码，文件已存为 UTF-8 **带 BOM**。

## 三、演示方案（3 场景，总时长 3-5 分钟）

> 完整话术与翻车预案见 `tools/演示手册.md`。这里给"演示前 Checklist + 时间线 + 验收标准"。

### 演示前 Checklist（5 分钟）
| 项 | 动作 | 通过标准 |
|---|---|---|
| 1 | 双击 `NetOpsLauncher.exe` | 控制台逐行输出，最后"启动完成 [OK]"，浏览器自动弹出 |
| 2 | 拓扑页点「立即刷新」 | 3 节点全绿；frr1 `OSPF Full/DR`；frr2/frr3 `eBGP Established` |
| 3 | （可选）对话问"在 frr1 上查看 OSPF 邻居状态" | Agent 调用工具，输出含 2.2.2.2 Full 的真实数据 |
| 4 | 演练前检查 | 对话输入演练话术，4 步闭环全 ok，拓扑页恢复全绿 |

### 时间线（面试现场 5 分钟版）
| 时间 | 动作 | 讲解要点 |
|---|---|---|
| 0:00-0:30 | 双击启动器 | 工程化交付：自检 Docker/容器/后端，自动拉起 |
| 0:30-1:30 | 拓扑页刷新 | 数据是 SSH 到真实 FRR 容器 `show` 出来的，非画图 |
| 1:30-3:30 | 输入故障演练话术 | 双通道模型（SSH 业务面 + docker exec 带外）+ ReAct 闭环 + 可逆故障 |
| 3:30-4:00 | 拓扑页看恢复 | 故障恢复后节点转绿，路由回表 |
| 4:00-5:00 | 收尾 | 一键恢复兜底 / 防幻觉 guard / 自研 ReAct 非黑盒 |

### 演示验收标准（每个场景"怎么算成功"）
1. **启动器**：不看任何文档，双击 exe → 浏览器自动打开 → 拓扑页 3 节点绿。
2. **拓扑页**：路由表里有 `O>*` 开头的 OSPF 路由；时间戳每 30s 自动变化。
3. **Agent 演练**：对话里出现 `frr_fault_inject` 4 次调用且全 ok；拓扑页中间出现过红色/断开，最终恢复绿色。
4. **抗追问**：能答出"为什么用 docker exec 恢复"（双通道）、"O 和 `>` 是什么"（OSPF 路由/活跃位）、"为什么不用 LangChain"（自研可控）。
